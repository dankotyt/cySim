# 0001. Многошаговый контракт сценария

- **Статус:** Superseded by [ADR-0007](0007-room-contract.md)
- **Дата:** 2026-11-12
- **Связано:** ADR-0003 (UI), ADR-0005 (корпус и артефакты)
- **Заменяет:** history_tasks/Answer_task_1111.md

> Решение пересмотрено в ADR-0007: перечисление шагов невозможно предусмотреть заранее и раздувает JSON. Ниже сохранено как история — почему отказались от графа.

## Context

- Текущий `scenarios` — один шаг: `title`, `content`, `actions[]`, `feedback`, `scoring`. Этого не хватает для «письмо → ссылка → форма» и для сценария «кликнул, но распознал и сообщил».
- Требование продукта: виртуальный рабочий день, где решение на одном шаге меняет следующий; итог зависит от всей цепочки, а не от одного клика.
- LLM надёжно пишет текст, но плохо держит длинный свободный JSON и тем более HTML. Вёрстка от LLM — это XSS и нестабильный UI.
- Веб-корпус (ADR-0005) уже даёт готовые артефакты: страницы сайтов, письма, PDF, USB-деревья, скрипты звонков. Их можно переиспользовать по ссылке.
- Неповторяемость нужна на уровне сценария, а не отдельного шага: одинаковые шаги в разной нити — нормально.

## Decision

Сценарий — **ориентированный граф шагов** со ссылками на артефакты корпуса. LLM собирает только нить (какие шаги, в каком порядке, какой текст и какие ссылки), UI — фиксированные компоненты.

```json
{
  "schema_version": "3.0",
  "id": "uuid",
  "tenant_id": "acme",
  "employee_id": "uuid",
  "rule_ids": ["uuid"],
  "rule_snapshot": ["..."],
  "topic": "phishing",
  "channel": "email_view",
  "mode": "practice",
  "difficulty": 3,
  "is_benign": false,
  "corpus_build_id": "corpus-2026-11-12",
  "entry_step_id": "s1",
  "steps": [
    {
      "id": "s1",
      "kind": "mail",
      "artifact_ref": "corpus-2026-11-12:email:em-0042",
      "actions": [
        {"id": "a1", "label": "Открыть вложение", "verdict": "unsafe", "next_step_id": "s2", "points": -10},
        {"id": "a2", "label": "Сообщить в ИБ", "verdict": "safe", "end": "end_safe", "points": 10}
      ]
    },
    {
      "id": "s2",
      "kind": "browser",
      "artifact_ref": "corpus-2026-11-12:site:br-0042-phish-1/login",
      "actions": [
        {"id": "b1", "label": "Ввести пароль", "verdict": "unsafe", "end": "end_compromised", "points": -10},
        {"id": "b2", "label": "Проверить домен и сообщить", "verdict": "safe", "end": "end_recovered", "points": 10}
      ]
    }
  ],
  "endings": [
    {"id": "end_safe", "kind": "safe", "title": "Угроза не дошла", "summary": "..."},
    {"id": "end_recovered", "kind": "recovered", "title": "Ошибка исправлена", "summary": "..."},
    {"id": "end_compromised", "kind": "compromised", "title": "Учётные данные утекли", "summary": "..."}
  ],
  "scoring": {"max_points": 16, "passing_score": 10},
  "meta": {"generator_version": "scenario-v3", "model": "...", "seed": 1, "fingerprint": "sha256:...", "degraded": false}
}
```

### Правила графа (L3)

1. Ровно **три терминальных узла**: `end_safe`, `end_compromised`, `end_recovered`; каждый объявлен в `endings` и достижим из `entry_step_id`.
2. Каждый не-терминальный шаг имеет 2–5 действий; каждое действие ведёт ровно в один `next_step_id` **или** в `end`.
3. Нет висячих ссылок: все `next_step_id` и `end` существуют в графе.
4. Нет недостижимых шагов и нет тупиков без `end`.
5. Циклы запрещены. Если сюжет требует возврата — это новый шаг; ограничение: ≤ 12 шагов, глубина ≤ 8.
6. Каждый `artifact_ref` существует в зафиксированном `corpus_build_id`.
7. На любом пути, ведущем в `end_compromised`, есть ≥ 1 подтверждённый признак (`evidence`), привязанный к полю артефакта.
8. `is_benign=true` не имеет `end_compromised`-пути (легитимный артефакт нельзя «скомпрометировать»).

### Скоринг

Итог считается по концовке, а не по сумме кликов:

```
outcome = safe | recovered | compromised
score   = clamp(round(max_points × outcome_multiplier) + verified_bonus, 0, max_points)
outcome_multiplier: safe = 1.0, recovered = 1.0, compromised = 0.0…0.3
verified_bonus: 0…2 (открыл сертификат/WhoIS, навёл на ссылку, проверил реквизиты)
```

`end_recovered` («кликнул, но распознал и сообщил») даёт **полный** балл наравне с `end_safe`: продукт учит распознаванию, а не «ни разу не ошибиться». `end_compromised` даёт частичный балл в зависимости от глубины: чем раньше сотрудник остановился, тем выше множитель.

### Хранение

- `scenarios.graph JSONB`, `entry_step_id`, `corpus_build_id`, `schema_version`, `max_points`; плоские `title/topic/department/status` остаются для списков и админки.
- `scenario_attempts(scenario_id, employee_id, path JSONB, ending_id, score, verified_flags)` — путь целиком, чтобы разбор в ЛК показывал, где именно сотрудник свернул не туда.
- Миграция — следующая после `0012`.

### Разделение ответственности

| Кто | Что делает |
|---|---|
| LLM | выбирает шаги, пишет текст, ссылается на существующие `artifact_ref`, расставляет вердикты |
| Валидатор | проверяет L0–L3; при нарушении — детерминированный ремонт (удалить битое ребро, подставить `end`) и повторная проверка, а не слепой retry |
| UI | рендерит шаг по `kind` фиксированным компонентом; HTML от LLM не исполняется никогда |
| Оценка | считает концовку и множитель; клиент не видит `verdict`, `points`, `endings` до ответа |

## Consequences

**Плюсы:** реалистичный сюжет; честная награда за распознавание; фиксированный UI исключает XSS и «поехавшую» вёрстку; граф проверяем автоматически; переиспользование артефактов корпуса удешевляет генерацию.

**Минусы и риски:** генератор и валидатор заметно сложнее (L3-граф, ремонт); нужен новый формат БД и миграция; оценка должна быть объяснимой для сотрудника; появляется соблазн «коротких» путей к `end_safe` — нужен контроль длины и покрытия шагов; артефакты корпуса становятся узким местом (нет артефакта — нет шага).

**Что поддерживать:** тесты инвариантов графа, версионирование схемы, `corpus_build_id` в каждом сценарии, миграции при изменении `steps[]`. До появления корпуса (M3) генератор работает на fixture-реестре артефактов того же формата.
