# 0007. Контракт «комната»: объекты, цель, ловушки

- **Статус:** Accepted
- **Дата:** 2026-11-12
- **Заменяет:** ADR-0001 (многошаговый граф) — он перечислял пути и раздувал JSON
- **Связано:** ADR-0002 (песочница), ADR-0003 (UI), ADR-0005 (корпус и артефакты)

## Context

- В графе ADR-0001 сценарий описывал **все шаги и переходы**. Это принципиально невозможно: сотрудник может сделать десятки осмысленных действий, а предусмотреть их заранее нельзя — получится тест с вариантами, а не обучение.
- Граф раздувал JSON (десятки шагов × действия × тексты), увеличивал выход LLM, стоил токенов и ломался на любом пропущенном `next_step_id`.
- Продукт должен вести себя как комната в TryHackMe: изолированная среда, где можно кликать по разным объектам и искать решение; задача решается несколькими способами, но есть действия, которые ломают прохождение.
- Отличие от THM: небезопасное действие **необратимо**. Сотрудник ввёл пароль на фальшивой странице — назад пути нет: штраф, мини-урок, зафиксированная ошибка.
- Один и тот же движок должен работать для письма, сайта, USB, звонка и PDF — значит, контракт не может быть «про email».
- Корпус (ADR-0005) уже знает про артефакт: легитимный он или нет, какие у него признаки и какое действие чем грозит. Дублировать это в каждом сценарии — лишняя работа.

## Decision

Сценарий — **комната**: набор объектов, цель и (опционально) дополнительные ловушки. Никаких шагов и переходов. Движок — событийный: UI присылает `(действие, объект)`, движок сверяет с рисками артефакта и решает исход.

```json
{
  "v": 4,
  "id": "sc_01J9Z6",
  "title": "Сверка за квартал",
  "topic": "phishing",
  "rule_ids": ["r1"],
  "diff": 3,
  "ttl": 600,
  "objs": [
    {"id": "m1", "kind": "email", "ref": "c2411:email:em-0042"},
    {"id": "w1", "kind": "site", "ref": "c2411:site:br-42/phish-1/login", "via": "m1:link:0"}
  ],
  "goal": "report(m1)",
  "extra": [
    {"on": "reply", "obj": "m1", "level": "soft", "pen": 2, "lesson": "L_REPLY_TO"}
  ]
}
```

Всё остальное — вне JSON:

| Что | Где живёт |
|---|---|
| Текст письма, HTML страницы, файлы USB | артефакт корпуса (`ref`) |
| Опасность действия (что именно ломает сценарий) | метаданные артефакта: `risk[]` |
| Легитимность артефакта | `benign` в артефакте |
| Текст мини-урока | библиотека `lessons` по `lesson` id |
| Баллы, множители, порог | вычисляются движком из `diff` и ленты событий |
| `tenant_id`, `employee_id`, `rule_snapshot`, модель, seed | колонки БД / назначение, не сценарий |

### Метаданные артефакта (корпус)

```yaml
- id: em-0042
  kind: email
  benign: false
  subject: "СРОЧНО: сверка за Q3"
  body: "..."
  risk:
    - {on: "download", level: "hard", pen: 10, lesson: "L_ATTACH_LNK"}
    - {on: "reply",    level: "soft", pen: 2,  lesson: "L_REPLY_TO"}
```

`risk[]` описывается один раз при сборке корпуса и переиспользуется во всех сценариях. Сценарий добавляет `extra[]` только для ситуационных ловушек (например, «коллега просит пароль по телефону»).

### Действия (единый словарь)

| `on` | Смысл | Где доступно |
|---|---|---|
| `open` | открыть объект | все |
| `inspect` | навести/посмотреть сертификат, WhoIS, свойства файла, номер | все |
| `click` | перейти по ссылке/кнопке | email, site |
| `download` | скачать вложение | email, site |
| `submit` | отправить форму (логин, пароль, код) | site |
| `reply` | ответить на письмо | email |
| `connect` | подключить USB | usb |
| `answer` | ответить на звонок | call |
| `speak` | сообщить информацию (код, пароль) | call |
| `report` | сообщить в ИБ | все |
| `dismiss` | закрыть/отклонить/не подключать | все |

Словарь фиксирован: UI не рисует кнопки из JSON, а показывает affordances, присущие типу объекта. Поэтому LLM не может выдумать действие, которого нет в интерфейсе.

### Цель

Предикат над лентой событий: `report(m1)`, `report(m1) && report(w1)`, `dismiss(m1) || report(m1)`. Грамматика: `verb(obj)`, `!`, `&&`, `||`, скобки. Цель монотонна — уже случившееся не отменяется.

Для легитимного артефакта цель — рабочее действие (`dismiss(m1)`), а `report` становится `soft`-ловушкой (ложное срабатывание). Так работает анти-«report-all».

### Исход и баллы

```
max   = 10 + 2 × diff                     # 12..20
score = clamp(max − Σ pen − blind, 0, max)
blind = 2, если цель достигнута без единого inspect
hard  → исход compromised, score = min(score, ⌊0.3 × max⌋), сценарий закрыт
goal  → safe (без soft) или recovered (были soft-ошибки)
ttl   → timeout, score = 0
```

- «Кликнул ссылку, но не вводил данные и сообщил» = `safe`, полный балл: клик сам по себе не ловушка.
- Ввод пароля, запуск вложения, подключение найденной флешки, передача кода — `hard`, без права на отмену.
- Ответ на подозрительное письмо, скачивание без открытия — `soft`: штраф и урок, прохождение продолжается.

### Инварианты

| Уровень | Что проверяется |
|---|---|
| **L0** | JSON по схеме, обязательные поля, `level ∈ {soft, hard}`, `diff ∈ [1, 5]`, `ttl ∈ [120, 1800]` |
| **L1** | `ref` существует в `corpus_build_id`; `via` разрешается в объект и affordance, циклов нет; глагол допустим для типа; `lesson` существует; `pen ≥ 0` |
| **L2** | grounding: урок из `risk`/`extra` привязан к правилу из `rule_ids` (через `rule_anchor`) |
| **L3** | цель парсится, выполнима, не выполнена на старте; `benign=false` → ≥ 1 `hard`; `benign=true` → ни одного `hard` и `report` даёт `soft`; ловушки не блокируют цель; объектов 1–5 |

Runtime-гарантии (не проверяются статически, обеспечиваются движком):

- неизвестное действие — нейтрально и пишется в ленту;
- `report` и `dismiss` доступны всегда, поэтому комната не может «застрять»;
- `hard` фиксирует исход, но UI продолжает показывать разбор;
- при несовпадении `corpus_build_id` комната не выдаётся, отдаётся fallback.

### Хранение

- `scenarios.room JSONB`, `schema_version`, `corpus_build_id`, `max_points`, `title`, `topic`, `rule_id`, `status`.
- `scenario_attempts(events JSONB, outcome, score, lessons[], started_at, finished_at)` — лента вместо «пути по графу»; по ней строится разбор «где именно ошибся».

## Consequences

**Плюсы:** JSON — 10–15 строк вместо десятков; выход LLM меньше в разы (дешевле и надёжнее); невозможно «не предусмотреть шаг», потому что шагов нет; тупиков нет по построению — выход (`report`/`dismiss`) есть всегда; один контракт на все каналы; обратная связь привязана к конкретному действию и признаку; несколько верных путей, свободное исследование.

**Минусы и риски:** меньше авторского контроля над сюжетом (нельзя срежиссировать «письмо → звонок → форма» жёстко); нужна дисциплина метаданных артефактов (`risk` пишется при сборке корпуса, а не в сценарии); библиотеку уроков надо курировать; возможен «случайный успех» (нажал report наугад) — лечится ложными срабатываниями на benign и штрафом `blind`; свободный текст («напишите, что вы сделали») не поддерживается — только фиксированные affordances.

**Что поддерживать:** словарь глаголов и таблицу «тип → affordances»; тесты инвариантов комнаты; согласованность `risk` артефакта и `lesson`; версия схемы; `corpus_build_id` в каждом сценарии.

## Что это меняет в прежних решениях

- ADR-0001 (граф) переведён в `Superseded by 0007`; `steps[]`, `next_step_id`, `endings`, `entry_step_id` больше не используются.
- Из сценария убраны `mode`, `tenant_id`, `employee_id`, `is_benign`, `scoring`, `meta` — это назначение, колонки БД и вычисляемые значения.
- `evidence` переехал в артефакт: сценарий не дублирует признаки, а ссылается на объект.
- Многошаговость сохраняется как **поведение**, а не как разметка: последовательность возникает из действий сотрудника и `via`, а не из заранее описанного графа.
