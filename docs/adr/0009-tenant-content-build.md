# 0009. Тенантная сборка артефактов и уроков

- **Статус:** Accepted
- **Дата:** 2026-11-17
- **Связано:** ADR-0005 (корпус и бренд-пак), ADR-0008 (контракт комнаты)

## Context

До этой вехи артефакты и уроки лежали в общем `fixtures/` и были одинаковыми для всех компаний. Это годилось, чтобы проверить движок M2, но противоречит смыслу продукта: сотрудник должен учиться **своей** политике — с названием своей компании, её порталами, контрагентами, формулировками регламента и указанием на конкретное правило.

При этом нельзя отдавать LLM то, что определяет оценку: `benign`, `risk[]`, `hard/soft`, `pen` и глагол-цель — это ground truth и формула балла. Если их сочиняет модель на компанию, оценка перестаёт быть доказуемой и воспроизводимой.

Отдельный риск — история: старая попытка должна показывать тот урок, который был в момент прохождения, а не текст из пересобранного корпуса.

## Decision

### Данные

| Таблица | Содержимое |
|---|---|
| `tenant_brand_packs` | `tenant_id`, `payload` (бренд компании, 2–3 контрагента, 1–2 сервиса, отрасль), `industry`, `created_at/updated_at`; правится админом по желанию |
| `tenant_builds` | `id` (`t-<tenant>-<n>`), `tenant_id`, `status` (`draft/ready/failed`), `stats`, `created_at/published_at` |
| `tenant_artifacts` | `build_id`, `artifact_id`, `kind`, `benign`, `intents`, `goal_actions` (JSON), `title`, `summary`, `content` (JSON: тело письма, поля страницы, реплики звонка), `risk` (JSON), `links`, `attachments`, `rule_id` |
| `tenant_lessons` | `build_id`, `lesson_id`, `rule_id`, `intent`, `title`, `text` |

`ref = <build_id>:<kind>:<artifact_id>`; `scenarios.corpus_build_id` пиннит сборку, поэтому пересборка не меняет старые комнаты.

### Разделение ответственности

- **Поведение** (`benign`, `risk[]`, `pen`, `hard/soft`, `goal_actions`) берётся из курируемого шаблона артефакта, а не из LLM; интент даёт только значение по умолчанию (ADR-0008, поправка 2026-11-17).
- **Контент** (отправитель, тема, текст, домен, реквизиты, название портала) пишет LLM по правилам компании и бренд-паку ADR-0005.
- **Урок** пишет LLM по тексту конкретного правила: 1–2 предложения, ссылка на действие из правила, без выдуманных требований. Урок привязан к `rule_id`, а не к артефакту. В fixtures уроки пока остаются курируемым каталогом; это данные, а не константы в коде.

### Пайплайн сборки

1. `regulations → brand_pack` (один LLM-шаг, кэш в `tenant_brand_packs`; отрасль — из текста или из 1–2 вопросов онбординга).
2. Для каждого правила — интент (кэш `security_rules.intent`) и исправленная тема (`topic`, ADR-0008).
3. Для каждого интента и полярности выбирается шаблон поведения; LLM пишет контент под бренд-пак: 1–2 опасных и 1 легитимный артефакт на интент. `goal_actions`, `benign`, `risk[]` и `pen` остаются из шаблона и не сочиняются моделью.
4. Для каждого обучаемого правила — урок (пачками по 10–20 правил на вызов).
5. Валидация сборки: у каждого интента есть обе полярности; `benign` без `hard`, опасные — с `hard`; у каждого артефакта непустой `goal_actions`, допустимый для его `kind`; уроки уникальны и привязаны к правилам; `ref` уникальны; в контенте нет реальных доменов и реальных брендов; нет ground truth в тексте.
6. `status=ready`, `published_at`; генерация комнат использует последнюю готовую сборку тенанта.

### Использование

- Реестр получает `for_tenant(session, tenant_id, build_id=None)`; без сборки — fallback на общий fixture (новый тенант работает сразу).
- Генерация комнаты берёт артефакты из сборки; `scenario.corpus_build_id` фиксирует её.
- `AttemptState` резолвит уроки по `scenario.corpus_build_id`, а не по последней сборке.
- Интенты остаются глобальным словарём из 15 значений: они отвечают за «что разыгрываем», бренд-пак — за «в каком мире».
- `topic` остаётся кросс-тенантным измерением аналитики; интенты для межкомпанийной аналитики не используются.

### Стоимость

Один бренд-пак + ~2 артефакта на интент (30) + уроки пачками (~15 вызовов на 124 правила) ≈ 45–50 LLM-вызовов на сборку тенанта; результат кэшируется до изменения правил.

## Consequences

**Плюсы:** сотрудник видит свою компанию и свою формулировку правила; оценка остаётся на курируемом ground truth; история попыток стабильна благодаря пиннингу сборки; ручной `brands.yaml` на тенанта не нужен.

**Минусы и риски:** стоимость и задержка первой сборки; качество контента зависит от регламентов (скудный текст → бедный бренд-пак); нужна валидация «нет реальных доменов/брендов»; пересборка при изменении правил должна быть явной, иначе сотрудники видят устаревшие уроки.

**Что поддерживать:** шаблоны поведения по интентам; пайплайн `regulations → brand_pack → artifacts → lessons`; резолв уроков по `build_id`; тест «каждый интент покрыт обеими полярностями в сборке»; запрет реальных доменов в валидаторе.
