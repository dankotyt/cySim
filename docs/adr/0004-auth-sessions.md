# 0004. Аутентификация и арендатор: серверные сессии + cookie

- **Статус:** Accepted
- **Дата:** 2026-11-12
- **Связано:** ADR-0002 (изоляция), ADR-0003 (SPA)

## Context

- Сейчас `tenant_id` приходит от клиента: `documents.py` (form/query), `scenarios.py` (query), `rules.py` (query). Любой, зная id, читает и удаляет данные чужой компании. Для multi-tenant это блокирующая проблема.
- Роли две: сотрудник и администратор (ИБ + руководитель). Администратор управляет отделами, документами, правилами, сценариями и видит аналитику.
- UI — SPA на том же origin, что API, поэтому cookie — естественный транспорт. Внешних API-клиентов и мобильных приложений пока нет.
- В open-source-инсталляциях ожидается локальная аутентификация «из коробки»; SSO/LDAP — пожелание enterprise-заказчиков, но не первого релиза.
- JWT в браузере требует решения про хранение (localStorage → XSS-риск, memory → перезагрузка), отзыв токенов и rotation. Для одного сервера это лишняя сложность.

## Decision

**Непрозрачная серверная сессия в HttpOnly-cookie; идентичность и арендатор — только из сессии.**

1. `sessions(id, employee_id, tenant_id, created_at, last_seen_at, expires_at, ip, user_agent, revoked_at)`; cookie `cs_session` — `HttpOnly; Secure; SameSite=Lax; Path=/`, TTL 12 часов со скользящим продлением, logout ставит `revoked_at`.
2. Пароли — Argon2id (`argon2-cffi`), минимальная длина 12, проверка на утечки — по списку слабых паролей, rate limit на логин (5 попыток / 15 минут на IP+логин).
3. `tenant_id`, `role`, `employee_id` берутся из сессии зависимостью `current_principal()`. Параметры `tenant_id` удаляются из всех публичных схем и query-параметров; чужой объект → 404 (не 403, чтобы не подтверждать существование).
4. CSRF: double-submit — сервер выдаёт `cs_csrf` (не HttpOnly) и требует заголовок `X-CSRF-Token` на `POST/PUT/PATCH/DELETE`. SPA читает cookie и подставляет заголовок.
5. RBAC: `employee`, `admin`. Проверка — на уровне зависимости и в репозиториях (фильтр по `tenant_id`). Отделы и сотрудники администрируются только `admin`.
6. MFA (TOTP) — обязательна для `admin` до первого production-развёртывания; для сотрудника опционально. Реализация может прийти позже, но поле `mfa_secret` и проверка в логине проектируются сразу.
7. SSO (OIDC) в будущем создаёт ту же серверную сессию после внешней проверки; роли маппятся на `employee/admin`. Это не меняет API.

### Переходный период

- Пока UI не готов, ручные проверки (`upload.html`) продолжают работать, но `tenant_id` в них берётся из временного dev-заголовка/сессии, а не из формы.
- Миграция: `sessions` + `employees` + `password_hash`; при первом запуске создаётся администратор из `ADMIN_EMAIL`/`ADMIN_PASSWORD` (переменные окружения, одноразовый bootstrap, затем пароль меняется).

## Consequences

**Плюсы:** сессию можно отозвать мгновенно; токен недоступен JS (XSS не крадёт сессию); нет проблем с rotation и хранением JWT; просто отлаживать; SSO подключается без смены контракта.

**Минусы и риски:** сессионная таблица и её очистка; CSRF-механика обязательна для всех мутаций; при горизонтальном масштабировании нужен общий store (сейчас БД — и это нормально); cookie требует HTTPS в production (Secure), а на localhost — исключение.

**Что поддерживать:** TTL и джоб очистки сессий; политику паролей; тесты «чужой арендатор → 404» для каждого эндпоинта; ротацию bootstrap-админа; аудит входов.
