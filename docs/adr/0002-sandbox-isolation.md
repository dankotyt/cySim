# 0002. Логическая изоляция песочницы сотрудника

- **Статус:** Accepted
- **Дата:** 2026-11-12
- **Связано:** ADR-0004 (auth), ADR-0005 (корпус)

## Context

- У каждого сотрудника должна быть «своя» среда: свой почтовый ящик, файлы, история браузера, назначенные сценарии, прогресс. Сосед по тенанту не должен видеть чужую почту и чужие ошибки.
- Продукт должен запускаться на одной машине разработчика и\или на одном сервере у заказчика; open-source-инсталляция не может требовать оркестратора.
- В песочнице нет ничего, что требует отдельного ядра: страницы корпуса статические, LLM вызывается только при генерации (заранее), UI — обычные веб-компоненты.
- Реальная изоляция «как в браузере» (контейнер/VM на сотрудника) стоит секунды на старт, гигабайты образов и отдельный слой эксплуатации. Для соло-разработки это неприемлемо на первом этапе.
- При этом «песочница» — не граница безопасности против злонамеренного сотрудника. Границу дают авторизация, отсутствие egress и sandbox-iframe.

## Decision

**Один backend, одна БД, логическая изоляция по `tenant_id + employee_id`.**

1. Всё состояние сотрудника — строки с его `employee_id`: `mailboxes`, `messages`, `files`, `browser_history`, `assignments`, `attempts`, `progress`. Запросы всегда фильтруются по сотруднику из сессии (ADR-0004), не по параметру запроса.
2. «Песочница» = персональное пространство + персональный набор назначенных сценариев + фиксированный UI (ADR-0003). Контейнеров, VM и отдельных браузерных профилей нет.
3. Страницы корпуса отдаются с отдельного origin в `<iframe sandbox="allow-forms">`; egress запрещён на уровне docker-сети и firewall (см. `backlog_security.md` п. 8). Это единственная «жёсткая» граница, и она общая для всех сотрудников.
4. Квоты на сотрудника: число сообщений в ящике, размер «файлов», число сессий — чтобы один сотрудник не раздул БД. Чистка старых событий по retention-политике.
5. Если в будущем понадобится сильная изоляция — выносим тенанта в отдельный деплой (тот же код, отдельные БД/контейнеры), а не дробим на сотрудников. Это отдельный ADR.

## Consequences

**Плюсы:** один процесс, один деплой, мгновенный старт сессии; состояние запрашивается обычным SQL; бэкап и миграции — как у обычного веб-приложения; дешево в эксплуатации; одинаково работает на ноутбуке и на сервере.

**Минусы и риски:** компрометация приложения раскрывает все песочницы тенанта — компенсируется RBAC, проверкой владения и аудитом; «шумный сосед» на уровне БД (тяжёлые выборки одного сотрудника) — индексы и лимиты; нет изоляции по CPU/памяти — при генерации сценариев нагрузка общая, поэтому генерация вынесена в очередь, а не в запрос пользователя.

**Что поддерживать:** дисциплина «идентичность только из сессии»; тесты на IDOR для каждого нового эндпоинта; retention-джоб; лимиты на размер пользовательских данных.
