# 0008. Контракт комнаты v1: объекты, цель, brief

- **Статус:** Accepted; amended by 0010
- **Дата:** 2026-11-16
- **Заменяет:** ADR-0007 (уточняет и сокращает контракт)
- **Связано:** ADR-0002 (песочница), ADR-0003 (UI), ADR-0004 (auth), ADR-0005 (корпус), ADR-0010 (brief пишет LLM)

## Context

ADR-0007 зафиксировал правильную идею: сценарий — комната, а не граф шагов. Но в его примере и в плане остались поля, которые при реализации M2 оказались лишними или вредными:

- `"v": 4` — версия схемы, которой не существует: контракт один, старые сценарии заменяются миграцией, а не читаются параллельно.
- `schema_version` в БД — то же самое, только колонкой.
- `ttl` — таймаут попытки. Он относится к «виртуальному дню» (M7), а не к комнате: у комнаты нет часов, и `timeout` без расписания нечем измерять.
- `extra[]` — ситуационные ловушки в самом сценарии. Они дублируют `risk[]` артефакта и заставляют LLM сочинять поведение, которое должно быть данными корпуса.
- В контракте не было текста задания: сотруднику показывали только объекты, а `goal` — предикат (`report(m1)`) — раскрывать нельзя, это ключ ответа.

Дополнительно выяснилось, что генератору нужен явный список допустимых объектов и правило «цель достижима без жёсткой ловушки», иначе модель стабильно ставит `hard` на действие, без которого цель не выполнить.

## Decision

Сценарий — **комната**: объекты, цель и краткое задание. Никаких шагов, переходов и концовок.

```json
{
  "v": 1,
  "title": "Сверка за квартал",
  "brief": "На рабочую почту пришло письмо с вложением от неизвестного отправителя. Что вы сделаете в этой ситуации?",
  "diff": 2,
  "objs": [
    {"id": "o1", "kind": "email", "ref": "fx:email:em-0001"},
    {"id": "w1", "kind": "site", "ref": "fx:site:s-0001", "via": "o1:link:0"}
  ],
  "goal": "report(o1)"
}
```

| Поле | Кто заполняет | Смысл |
|---|---|---|
| `v` | система/модель | версия контракта, всегда `1` |
| `title` | модель | 3–120 символов |
| `brief` | модель | 20–400 символов: наблюдаемая ситуация и вопрос «что вы сделаете?»; **без действия, оценки и правильного ответа** — требование промпта (ADR-0010) |
| `diff` | модель | 1–5, задаёт `max = 10 + 2 × diff` |
| `objs` | модель | 1–5 объектов, `id` уникален, `ref` только из каталога |
| `via` | модель | `<id>:link:<index>` — объект открывается по ссылке из другого |
| `goal` | модель | предикат над лентой событий, **не отдаётся клиенту**; действие обязано совпасть с `goal_actions` артефакта |
| `topic` | система | тема правила (аналитика), модель её не придумывает |
| `intent` | система | интент комнаты: что именно разыгрывается; выбирается по тексту правила |

Типы объектов: `email`, `site`, `pdf`, `usb`, `call`, `workstation`, `desk`, `door`, `badge`.
Глаголы фиксированы: `open`, `inspect`, `click`, `download`, `submit`, `reply`, `connect`, `answer`, `speak`, `report`, `dismiss`, `lock`, `leave`, `shred`, `scan`, `escort`, `wear`, `share`, `return`.

### Что осталось вне JSON

| Что | Где живёт |
|---|---|
| Контент письма, HTML страницы, файлы | артефакт корпуса (`ref`) |
| `benign` и `risk[]` (действие, уровень, штраф, урок) | метаданные артефакта |
| Правильное действие (`goal_actions`) | метаданные артефакта; интент даёт только дефолт |
| Текст мини-урока | контент артефакта/сборки: fixtures — каталог `lessons`, тенант — ADR-0009 |
| Баллы, `max_points`, исход | движок |
| `tenant_id`, `employee_id`, `rule_snapshot`, `corpus_build_id` | колонки БД |
| Время | «виртуальный день» (M7), не комната |

`extra[]` не используется: любая ловушка обязана быть свойством артефакта, иначе её нельзя проверить на консистентность и переиспользовать в других комнатах.

### Интенты и каналы

Тема правила — аналитический тег, слишком широкий для выбора объектов: `access_control` покрывает и общий диск, и экран, и пропуск. Поэтому комната привязана к **интенту** — фиксированному описанию ситуации (`app/core/intents.py`):

| Интент | Канал | Действие по умолчанию (опасная комната) |
|---|---|---|
| `phishing_email`, `attachment_macro`, `credential_form`, `usb_found`, `phone_code`, `remote_tool`, `invoice_change`, `data_disclosure`, `password_sharing` | email / site / pdf / usb / call | `report` |
| `unattended_session`, `shoulder_surfing`, `clean_desk` | workstation / desk | `lock` |
| `tailgating`, `visitor_handling` | door / badge | `escort` (артефакты объявляют `report`) |
| `badge_sharing` | badge | `report` |

Это **только значения по умолчанию**. Артефакт объявляет собственный `goal_actions`; валидатор L3 принимает только действие, объявленное у выбранного артефакта. Для легитимной комнаты действие тоже объявляет артефакт (`dismiss`, `leave`, `scan`, `wear`), а не таблица интентов: один и тот же интент может требовать `scan` для проверки пропуска и `report` для нарушения.

Правило классифицируется по **своему тексту** (не по теме) отдельным LLM-шагом; результат кэшируется в `security_rules.intent`. Ответ `not_representable` означает, что правило описывает процесс или роль, а не действие сотрудника: такое правило в пачке попадает в `skipped_details` с причиной, а не получает случайную комнату. Значение темы в поле `intent` не принимается: после одного корректирующего повтора правило уходит в `skipped_details` с причиной `invalid_intent` (или `invalid_json`). Уже закэшированное в БД значение вне `INTENTS` переклассифицируется. Если для интента нет артефакта нужной полярности — слот тоже пропускается с причиной `no_threat_artifact`/`no_benign_artifact`.

Для легитимных комнат правильное действие — «рабочее» (`dismiss`, `leave`, `scan`, `wear`), а `report` даёт `soft`-штраф. Конкретное действие объявляет артефакт; пара `threat_verb`/`benign_verb` в описании интента остаётся только дефолтом для артефактов без явного `goal_actions`.

### Цель и исход

Грамматика: `verb(obj)`, `!`, `&&`, `||`, скобки. Цель монотонна — уже случившееся не отменяется.

```
max   = 10 + 2 × diff                       # 12..20
score = clamp(max − Σpen − blind, 0, max)
blind = 2, если цель достигнута без inspect И действия шли серией:
        ≥ 3 действий с интервалом ≤ 2 с (осмысленный первый ответ не штрафуется)
hard  → failed, score = 1, комната закрыта
goal  → safe (без soft) | recovered (были soft)
иначе → in_progress
```

- Легитимный артефакт: цель — действие, объявленное артефактом (`dismiss`, `scan`, `wear`, `leave`), а `report` даёт `soft`-штраф 2 и урок `L_FALSE_POSITIVE` (анти-«report-all»).
- Жёсткая ловушка необратима: ввод пароля, запуск вложения, подключение найденной флешки, передача кода. Она закрывает комнату с исходом `failed` и одним баллом; `pen=10` в артефакте остаётся данными, но в публичной ленте не показывается как «−10».
- `blind` — не «ответ с первой попытки», а признак прокликивания: три и более действий подряд с интервалом не больше двух секунд без единого `inspect`.
- Таймаута и исхода `timeout` в v1 нет: комната не имеет собственных часов.

### Инварианты (L0–L3)

| Уровень | Что проверяется |
|---|---|
| **L0** | `v == 1`; обязательные поля; `objs` 1–5, `id` уникальны; `diff ∈ [1,5]`; `goal` парсится; `brief` проверяется только по схеме и длине |
| **L1** | `ref` есть в реестре; `kind` совпадает; `via` разрешается в существующий объект и индекс ссылки; глагол допустим для типа объекта; уроки существуют |
| **L2** | grounding: каждый артефакт с `hard`-риском помечен интентом комнаты; хотя бы один объект привязан к интенту |
| **L3** | цель не выполнена на старте; в цели есть действие, объявленное артефактом (`goal_actions`) или дефолтом интента; нет `report` легитимного; ни один положительный литерал не является `hard`; `benign` без `hard`, опасный — хотя бы с одним `hard` |

Проверки L0–L3 — статические; неизвестное действие в рантайме нейтрально и пишется в ленту. `report` и `dismiss` доступны всегда, поэтому комната не может «застрять».

### Генерация

1. Правило классифицируется в интент (LLM по тексту правила, кэш в `security_rules.intent`); `not_representable` — правило пропускается.
2. Планнер выбирает до 10 артефактов этого интента: до 8 нужной полярности + 2 дистрактора. В опасной комнате дистракторы легитимные, в легитимной — тоже легитимные (иначе L3 отклоняет комнату); выбор детерминирован по `tenant_id/rule_id/intent/полярность/попытка`.
3. В каталог промпта входит `goal_actions` каждого артефакта; модель пишет `title`, `brief`, `objs` и `goal`, но цель обязана совпасть с объявленной у выбранного артефакта. Системные поля `topic`/`intent` добавляются после разбора; few-shot строится из `summary` реального объекта, а brief — из наблюдаемой ситуации, без действия и оценки.
4. L0–L3; при ошибке — до 3 попыток, в промпт добавляются нарушения и компактное описание отклонённой комнаты, а её объекты исключаются из каталога повтора. Содержательные требования к `brief` живут в промпте (ADR-0010); L0 проверяет только схему и длину.
5. Структурный `fingerprint = sha256(intent + goal + отсортированные refs)`; совпадение с комнатой тенанта — тоже повод для повтора. Тема в fingerprint не входит: она аналитическая, а не смысловая. После второго дубликата генерация сразу уходит в fallback.
6. После 3 неудач (2 для дубликатов) — детерминированная fallback-комната нужной полярности из fixture-реестра (без LLM).
7. Пачка: `rooms_per_rule` комнат на правило (по умолчанию 2); доля benign-слотов задаётся `benign_ratio` (по умолчанию 0.2) и распределяется детерминированно по хэшу `(rule_id, room_index)`. Слоты без подходящего артефакта попадают в `skipped_details` с причиной.

Эмбеддинг-near-dup отложен до M9: структурный fingerprint уже отсекает «то же письмо с другим заголовком».

### Публичный и приватный DTO

- `PublicScenario` — `title`, `brief`, `topic`, `diff`, `max_points`, `objs[{id, kind, ref, via}]`. Без `goal`, `benign` и `risk`.
- Полный `Scenario` (с `room.goal`) возвращает только эндпоинт генерации, то есть оператор/админ.
- После действия клиент получает уровень, штраф и мини-урок — это обратная связь, а не ключ ответа. У hard-события `pen = 0` в публичной ленте (иначе «−10» читается как продолжение комнаты), исход попытки — `failed`.

### Хранение

- `scenarios.room` — весь контракт; рядом `title`, `topic`, `diff`, `max_points`, `fingerprint`, `corpus_build_id`, `rule_snapshot`, `deleted_at`.
- Колонки `rule_id` нет: правило определяется `rule_snapshot.id`, поэтому одна и та же связь не хранится дважды. Выборки по правилу и каскадное скрытие при его удалении идут по JSON-копии снимка.
- `scenario_attempts(id, tenant_id, scenario_id, employee_id, events, outcome, score, max_points, lessons, started_at, finished_at)`.
- `security_rules.intent` — кэш классификации (`NULL` = ещё не классифицировано); миграция `0015`.
- `scenario_attempts.outcome` — `in_progress | safe | recovered | failed`; миграция `0016` переписывает старые `compromised` в `failed`.
- `employee_id` берётся из запроса (как `tenant_id` до M3); после M3 — из сессии.
- Миграция `0014` удаляет колонки плоского сценария. Строки, созданные до неё, остаются с `room = NULL` и приложением не читаются — их можно удалить вручную.

## Consequences

**Плюсы:** JSON — 8 строк; выход модели короткий и проверяемый; поведение живёт в данных корпуса и переиспользуется; правильный ответ объявляет артефакт, а интент связывает комнату с правилом по смыслу; у сотрудника есть текст задания, а ключ ответа остаётся на сервере; 20/80 задаётся параметром пачки.

**Минусы и риски:** классификация интента — ещё один LLM-вызов на правило (кэшируется); правила, не сводимые к действию сотрудника, остаются без обучения до появления новых артефактов/каналов; нет таймаута — попытка может висеть открытой (закроется вместе с виртуальным днём в M7); fallback-комнаты однообразнее сгенерированных; `employee_id` из запроса — временный долг M3; `goal_actions` нужно поддерживать в каждом артефакте, иначе комната тихо откатится к дефолту интента.

**Что поддерживать:** словарь интентов и таблицу «интент → каналы»; `goal_actions` и `risk[]`/`lesson` в реестре артефактов; словарь глаголов и affordances по типу; покрытие каждого интента обеими полярностями (тест в `test_intents.py`); каталог fixture-артефактов до появления корпуса (M6).

## Что это меняет в ADR-0007

- Убраны `extra[]`, `ttl`, `schema_version`; версия контракта — только `room.v = 1`.
- Добавлен `brief` как единственный источник задания для сотрудника.
- Зафиксированы конкретные проверки L0–L3, правило достижимости цели и правило `benign`.
- Добавлены структурный fingerprint, fallback-комната и таблица попыток.
- ADR-0007 переведён в `Superseded by 0008`; история решения сохранена.

## Поправка 2026-11-17

- Правильное действие объявляет артефакт (`goal_actions`), а таблица интентов остаётся только дефолтом. Пример: `visitor_handling` для легитимного посетителя требует `scan`, для курьера в служебной зоне — `report`; `escort` в обоих случаях остаётся soft-ловушкой, а не универсальным ответом.
- `brief` пишет LLM по контракту промпта: только наблюдаемая ситуация и вопрос, без действия и оценки (ADR-0010). L0 проверяет только схему и длину; лексическая регулярка не используется. Fallback-текст строится из `summary`, а не из шаблона «В работе появился объект…».
- Жёсткая ловушка даёт `failed` и 1 балл вместо `compromised` и 30% `max`; в публичной ленте hard-событие не показывается как «−10».
- `blind` срабатывает на серию быстрых нажатий (≥3 действий, интервал ≤2 с) без `inspect`, а не на первый успешный ответ.
- Уроки — контент артефакта/сборки (ADR-0009), а не константы интента.
- Последовательные проверки (`scan`/`inspect` перед `escort`) отложены до UI-движка (M7): набор affordances должен быть зафиксирован, иначе предусловие не на что опереть. До этого такие действия остаются обычными soft-штрафами.
