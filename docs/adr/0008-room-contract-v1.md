# 0008. Контракт комнаты v1: объекты, цель, brief

- **Статус:** Accepted
- **Дата:** 2026-11-16
- **Заменяет:** ADR-0007 (уточняет и сокращает контракт)
- **Связано:** ADR-0002 (песочница), ADR-0003 (UI), ADR-0004 (auth), ADR-0005 (корпус)

## Context

ADR-0007 зафиксировал правильную идею: сценарий — комната, а не граф шагов. Но в его примере и в плане остались поля, которые при реализации M2 оказались лишними или вредными:

- `"v": 4` — версия схемы, которой не существует: контракт один, старые сценарии заменяются миграцией, а не читаются параллельно.
- `schema_version` в БД — то же самое, только колонкой.
- `ttl` — таймаут попытки. Он относится к «виртуальному дню» (M7), а не к комнате: у комнаты нет часов, и `timeout` без расписания нечем измерять.
- `extra[]` — ситуационные ловушки в самом сценарии. Они дублируют `risk[]` артефакта и заставляют LLM сочинять поведение, которое должно быть данными корпуса.
- В контракте не было текста задания: сотруднику показывали только объекты, а `goal` — предикат (`report(m1)`) — раскрывать нельзя, это ключ ответа.

Дополнительно выяснилось, что генератору нужен явный список допустимых объектов и правило «цель достижима без жёсткой ловушки», иначе модель стабильно ставит `hard` на действие, без которого цель не выполнить.

## Decision

Сценарий — **комната**: объекты, цель и краткое задание. Никаких шагов, переходов и концовок.

```json
{
  "v": 1,
  "title": "Сверка за квартал",
  "brief": "На рабочую почту пришло письмо с вложением от неизвестного отправителя. Решите, что делать с письмом и вложением, действуя по политике компании.",
  "diff": 2,
  "objs": [
    {"id": "o1", "kind": "email", "ref": "fx:email:em-0001"},
    {"id": "w1", "kind": "site", "ref": "fx:site:s-0001", "via": "o1:link:0"}
  ],
  "goal": "report(o1)"
}
```

| Поле | Кто заполняет | Смысл |
|---|---|---|
| `v` | система/модель | версия контракта, всегда `1` |
| `title` | модель | 3–120 символов |
| `brief` | модель | 20–400 символов: ситуация и задача, **без подсказки ответа** |
| `diff` | модель | 1–5, задаёт `max = 10 + 2 × diff` |
| `objs` | модель | 1–5 объектов, `id` уникален, `ref` только из каталога |
| `via` | модель | `<id>:link:<index>` — объект открывается по ссылке из другого |
| `goal` | модель | предикат над лентой событий, **не отдаётся клиенту** |
| `topic` | система | тема правила, модель её не придумывает |

Типы объектов: `email`, `site`, `pdf`, `usb`, `call`. Глаголы фиксированы: `open`, `inspect`, `click`, `download`, `submit`, `reply`, `connect`, `answer`, `speak`, `report`, `dismiss`.

### Что осталось вне JSON

| Что | Где живёт |
|---|---|
| Контент письма, HTML страницы, файлы | артефакт корпуса (`ref`) |
| `benign` и `risk[]` (действие, уровень, штраф, урок) | метаданные артефакта |
| Текст мини-урока | каталог `lessons` |
| Баллы, `max_points`, исход | движок |
| `tenant_id`, `employee_id`, `rule_snapshot`, `corpus_build_id` | колонки БД |
| Время | «виртуальный день» (M7), не комната |

`extra[]` не используется: любая ловушка обязана быть свойством артефакта, иначе её нельзя проверить на консистентность и переиспользовать в других комнатах.

### Цель и исход

Грамматика: `verb(obj)`, `!`, `&&`, `||`, скобки. Цель монотонна — уже случившееся не отменяется.

```
max   = 10 + 2 × diff                       # 12..20
score = clamp(max − Σpen − blind, 0, max)
blind = 2, если цель достигнута без единого inspect
hard  → compromised, score = min(score, ⌊0.3 × max⌋), комната закрыта
goal  → safe (без soft) | recovered (были soft)
иначе → in_progress
```

- Легитимный артефакт: цель — рабочее действие (`dismiss`), а `report` даёт `soft`-штраф 2 и урок `L_FALSE_POSITIVE` (анти-«report-all»).
- Жёсткая ловушка необратима: ввод пароля, запуск вложения, подключение найденной флешки, передача кода.
- Таймаута и исхода `timeout` в v1 нет: комната не имеет собственных часов.

### Инварианты (L0–L3)

| Уровень | Что проверяется |
|---|---|
| **L0** | `v == 1`; обязательные поля; `objs` 1–5, `id` уникальны; `diff ∈ [1,5]`; `goal` парсится |
| **L1** | `ref` есть в реестре; `kind` совпадает; `via` разрешается в существующий объект и индекс ссылки; глагол допустим для типа объекта; уроки существуют |
| **L2** | grounding: у каждого артефакта с `hard`-риском тема правила входит в его `topics`; хотя бы один объект привязан к теме |
| **L3** | цель не выполнена на старте; в цели есть `report` опасного объекта; нет `report` легитимного; ни один положительный литерал цели не является `hard`; `benign` без `hard`, опасный — хотя бы с одним `hard` |

Проверки L0–L3 — статические; неизвестное действие в рантайме нейтрально и пишется в ленту. `report` и `dismiss` доступны всегда, поэтому комната не может «застрять».

### Генерация

1. Планнер выбирает до 12 артефактов, привязанных к теме правила (9 опасных + 3 легитимных), детерминированно по `tenant_id/rule_id/попытка`.
2. Модель возвращает JSON; системное поле `topic` добавляется после разбора.
3. L0–L3; при ошибке — до 3 попыток, в промпт добавляется список нарушений.
4. Структурный `fingerprint = sha256(topic + goal + отсортированные refs)`; совпадение с комнатой тенанта — тоже повод для повтора.
5. После 3 неудач — детерминированная fallback-комната из fixture-реестра (без LLM), чтобы правило всегда давало упражнение.

Эмбеддинг-near-dup отложен до M9: структурный fingerprint уже отсекает «то же письмо с другим заголовком».

### Публичный и приватный DTO

- `PublicScenario` — `title`, `brief`, `topic`, `diff`, `max_points`, `objs[{id, kind, ref, via}]`. Без `goal`, `benign` и `risk`.
- Полный `Scenario` (с `room.goal`) возвращает только эндпоинт генерации, то есть оператор/админ.
- После действия клиент получает уровень, штраф и мини-урок — это обратная связь, а не ключ ответа.

### Хранение

- `scenarios.room` — весь контракт; рядом `title`, `topic`, `diff`, `max_points`, `fingerprint`, `corpus_build_id`, `rule_snapshot`, `deleted_at`.
- Колонки `rule_id` нет: правило определяется `rule_snapshot.id`, поэтому одна и та же связь не хранится дважды. Выборки по правилу и каскадное скрытие при его удалении идут по JSON-копии снимка.
- `scenario_attempts(id, tenant_id, scenario_id, employee_id, events, outcome, score, max_points, lessons, started_at, finished_at)`.
- `employee_id` берётся из запроса (как `tenant_id` до M3); после M3 — из сессии.
- Миграция `0014` удаляет колонки плоского сценария. Строки, созданные до неё, остаются с `room = NULL` и приложением не читаются — их можно удалить вручную.

## Consequences

**Плюсы:** JSON — 8 строк; выход модели короткий и проверяемый; поведение живёт в данных корпуса и переиспользуется; у сотрудника есть текст задания, а ключ ответа остаётся на сервере; нет полей «на будущее», которые никто не читает.

**Минусы и риски:** нет таймаута — попытка может висеть открытой (закроется вместе с виртуальным днём в M7); fallback-комнаты однообразнее сгенерированных; структурный fingerprint не ловит перефразированные комнаты из других артефактов; `employee_id` из запроса — временный долг M3.

**Что поддерживать:** словарь глаголов и таблицу «тип → affordances»; согласованность `risk[]`/`lesson` в реестре; каталог fixture-артефактов до появления корпуса (M6); тесты инвариантов комнаты.

## Что это меняет в ADR-0007

- Убраны `extra[]`, `ttl`, `schema_version`; версия контракта — только `room.v = 1`.
- Добавлен `brief` как единственный источник задания для сотрудника.
- Зафиксированы конкретные проверки L0–L3, правило достижимости цели и правило `benign`.
- Добавлены структурный fingerprint, fallback-комната и таблица попыток.
- ADR-0007 переведён в `Superseded by 0008`; история решения сохранена.
