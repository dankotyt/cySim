# Plan-schedule — дорожная карта CyberSim

План доведения проекта до релиза: архитектурное решение для «браузера внутри стенда», потоки работ, вехи с пояснениями (зачем сейчас, что может пойти не так, на что смотреть), правила пересмотра. Дополняет `docs/adr/0007-room-contract.md` (контракт сценария) и `backlog_security.md` (безопасность).

---

## 0. Как читать план

Методология — гибкая, rolling wave: детально расписаны ближайшие 2–3 вехи, дальние — крупными блоками. Требования доопределяются по ходу, поэтому план пересматривается на каждой вехе.

| Правило | Как применяем |
|---|---|
| Итерация | 2 недели, заканчивается демо и обновлением бэклога |
| Веха | Проверяемый инкремент: «можно показать и измерить», а не «код написан» |
| Гейт (G) | Решение go / no-go / cut-scope по явным критериям |
| Буфер | 20% ёмкости не планируется (итерации 12–13 — гейты и резерв) |
| Неопределённость | Оформляется как spike (1–3 дня) с решением и ADR, а не как «потом разберёмся» |
| Даты | Календарные даты фиксируем только после M0; до этого — итерации и зависимости |
| Урезание | Режем объём (бренды, каналы, геймификацию), никогда — безопасность и целостность оценки |

Обозначения размера: **S** — до 3 дней, **M** — до 1 итерации, **L** — 1–2 итерации, **XL** — 2+ итерации.

## 1. Архитектурное решение: синтетический веб-корпус

### 1.1 Принцип

Строим **мини-интернет стенда** из данных, а не из ручной вёрстки:

```
brands.yaml ─┐
layouts/     ├─> build_corpus.py (CI) ─> corpus/<build_id>/<host>/<path>.html
copy_packs/  ┘                              │
mutations.yaml ─────────────────────────────┘
                                            ▼
                          site-service (allowlist хостов) ─> iframe в браузере стенда
                                            │
                          site_instances (ground truth: is_phishing, mutation, difficulty)
                                            ▼
                                   только scoring-сервис
```

Три правила, на которых всё держится:

1. **Домен — единственный надёжный признак**, поэтому мутация всегда меняет домен, а остальные сигналы (сертификат, whois, реквизиты, форма) меняются выборочно — чтобы нельзя было выучить один признак.
2. **Ground truth никогда не попадает в HTML.** Вердикт хранится в БД и доступен только оценке.
3. **Контент генерируется на сборке, а не на запрос.** LLM в рантайме стенда не участвует.

### 1.2 Почему синтетические компании, а не реальные

Клонировать сайты реальных компаний нельзя: товарные знаки, авторское право, риск «обучения на настоящем фишинге» и претензий. Поэтому:

- бренды вымышленные (`ООО «Ромашка-Пром»`, `АО «Вектор-Снаб»`), генерируются из словарей и проверяются на совпадение с известными марками;
- домены выглядят правдоподобно (`.ru`, `.com`, `.online`), но проверяются на NXDOMAIN при сборке и живут только внутри стенда;
- egress запрещён, поэтому «настоящий» домен в стенде недостижим в принципе;
- если корпус когда-нибудь будет опубликован — переключаемся на `.example`/`.test` (флаг сборки).

### 1.3 Реестр брендов (данные, не код)

```yaml
- id: br-0001
  slug: romashka-prom
  display_name: ООО «Ромашка-Пром»
  legal_name: Общество с ограниченной ответственностью «Ромашка-Пром»
  inn: "7701234567"          # синтетический, но checksum-валидный
  industry: retail            # retail | finance | it | hr | medicine | logistics | ...
  domain: romashka-prom.ru
  palette: {primary: "#1f6feb", accent: "#f2c94c"}
  monogram: РП
  layout: 3                   # 1..4
  pages: [home, about, contacts, login, support]
  contacts: {phone: "+7 495 000-00-01", email: "info@romashka-prom.ru"}
  cert: {issuer: "Russian Trusted CA", since: 2022-04-01}
```

Добавление компании = одна запись YAML + пересборка. Это и есть «общая база, которая пополняется».

### 1.4 Дёшево: из чего складывается разнообразие

| Механика | Даёт | Стоимость |
|---|---|---|
| 4 layout-шаблона (Jinja2) | разная структура страниц | 4 файла |
| 8 палитр + 4 шрифтовых стека | визуальная непохожесть | 1 CSS-токен-файл |
| Монограмма вместо логотипа (SVG) | «свой» бренд без картинок | 0 |
| 10 отраслевых пакетов текста (по 15–20 фраз) | отраслевой язык | 200 строк |
| Комбинаторика 4×8×10 = 320 | визуальных вариаций | 0 |

Никаких фотографий: градиенты, геометрия, SVG-иконки. Если нужны «люди» — один лицензированный набор из 20–30 изображений, переиспользуется во всех брендах.

**Объём и цена:**

| Параметр | Значение |
|---|---|
| 1000 брендов × 6 страниц | 6 000 страниц |
| клоны: ~2,5 на бренд × 2 страницы | ~5 000 страниц |
| средний вес страницы | ~20 КБ |
| итого корпус | ~220 МБ |
| сборка | 2–5 минут CPU (без GPU) |
| рантайм | 1 контейнер (nginx/Caddy) + read-only volume |
| стоимость на запрос | ≈ 0 (никакого LLM) |

### 1.5 Матрица мутаций

| Мутация | Пример | Сложность | Что ещё меняется |
|---|---|---|---|
| Пропуск символа | `romashka-prom.ru` → `romashka-prm.ru` | 1 | ничего (только домен) |
| Перестановка | `romashka` → `romaskha` | 1 | ничего |
| Подмена `rn→m`, `l→1`, `o→0` | `romashka` → `r0mashka`, `barn` → `bam` | 2 | иногда шрифт/логотип «плывёт» |
| Гомоглиф (кириллица) | `romashka.ru` → `rоmаshkа.ru` | 3 | punycode в адресной строке |
| Смена TLD | `.ru` → `.online`, `.shop`, `.site` | 1 | сертификат другой CA |
| Дефис/суффикс | `romashka-prom.ru` → `romashka-prom-support.ru` | 1 | «служба поддержки» в шапке |
| Поддомен | `romashka-prom.ru.secure-login.ru` | 3 | замок есть, домен — чужой |
| Ключевое слово | `romashka-prom-pay.ru` | 2 | форма оплаты |
| Punycode-домен | `xn--80a...` | 3 | в панели — «кириллический домен» |

Для каждого клона задаётся ровно 1–3 изменённых сигнала из набора: `domain`, `cert`, `whois_age`, `legal_name`, `phone`, `form_action`, `footer`.

### 1.6 Что сотрудник может проверить

| Проверка | Источник данных | Как влияет на оценку |
|---|---|---|
| Адрес и выделение eTLD+1 | адресная строка | основной признак |
| Панель сертификата (CN, issuer, срок, self-signed) | `site_instances.cert` | событие `check_cert` → бонус `verified` |
| WhoIS (дата регистрации, регистратор) | `site_instances.whois` | `check_whois` |
| Реквизиты в подвале (юрлицо, ИНН, телефон) | HTML страницы | `check_contacts` |
| Наведение на ссылку (полный адрес) | HTML страницы | `hover_link` |
| Поиск «официальный сайт компании» | внутренний индекс | `search_used` |

Внутренний поиск отдаёт смешанные вердикты: часть результатов подтверждает официальный домен, часть нейтральна, часть «опровергает» — но опровержение существует только для легитимных сайтов. Иначе сотрудник выучит стратегию «искать подтверждение своей гипотезы». Ранжирование детерминировано по `world_id`, поэтому у всех сотрудников тенанта одна и та же картина мира.

События проверок пишутся в телеметрию; если сотрудник достиг цели без единого `inspect`, движок снимает 2 балла (`blind`, ADR-0007). Так «обязан всё перепроверить» становится измеримым, а не декларативным.

### 1.7 Качество корпуса: сборка не пройдёт, если…

1. ссылка ведёт на хост, которого нет в реестре (битые ссылки и «случайные» домены);
2. на легитимной странице есть опечатка в названии компании, чужой ИНН или другой телефон (случайный сигнал — сотрудник выучит ложь);
3. клон отличается от оригинала не только заявленными сигналами (проверка «ровно N мутаций»);
4. на странице есть JS, внешние ресурсы или абсолютные URL на реальные сайты;
5. страница тяжелее 60 КБ или ломается на 1280×720 (Playwright-скриншот для 4 layout × 8 палитр);
6. в тексте встречаются «это фишинг», lorem ipsum, служебные пометки;
7. у артефакта нет `evidence_anchors`, на которые ссылается урок.

### 1.8 Anti-memorization

- **Мир на арендатора:** `world_id = HMAC(world_secret, tenant_id || corpus_build)` задаёт перестановку «бренд → домен». В компании A `romashka-prom.ru` — настоящий сайт, в компании B — клон. Общая база одна, ответы не переносятся между тенантами.
- Внутри тенанта мир стабилен — это фича: у сотрудника есть «сайт своей компании», который он должен знать.
- Сотрудник видит не весь корпус, а выборку; лимит навигации на сессию мешает выкачать корпус и построить таблицу «host → вердикт».
- Каждый сценарий ссылается на `artifact_ref`; объекты с неизвестным артефактом отбраковываются на L3.

### 1.9 Что не делать

- не клонировать реальные сайты, логотипы и тексты;
- не рендерить страницы LLM на каждый запрос;
- не поднимать реальный DNS/TLS и не проксировать внешние URL;
- не давать страницам JavaScript;
- не делать 1000 уникальных дизайнов руками;
- не хранить `is_phishing` в HTML, JS или имени файла.

### 1.10 Реестр артефактов

Сценарий (ADR-0007) не хранит HTML и текст писем — он ссылается на артефакт:

```
artifact_ref = "<corpus_build_id>:<kind>:<id>"      # corpus-2026-11-12:email:em-0042
```

| `kind` | Что внутри | Кто рендерит |
|---|---|---|
| `site_page` | HTML страницы + trust-метаданные | `BrowserApp` (iframe) |
| `email` | отправитель, тема, тело, вложения, ссылки | `MailApp` |
| `pdf` | сгенерированный PDF + метаданные файла | `PdfViewer` |
| `usb_tree` | метка носителя, файлы, autorun | `UsbDialog` |
| `call_script` | звонящий, реплики, запрос, политика проверки | `PhoneApp` |

Каждый артефакт несёт **поведение**, а не только контент:

```yaml
benign: false
risk:
  - {on: "download", level: "hard", pen: 10, lesson: "L_ATTACH_LNK"}
  - {on: "reply",    level: "soft", pen: 2,  lesson: "L_REPLY_TO"}
evidence_anchors: ["attachments[0].name", "links[0].href"]
```

Правила:

- пул ≥ 25 артефактов на тему (18 тем → ≥ 450, цель 600), распределение по каналам;
- один артефакт может встречаться в разных сценариях, но **не у одного сотрудника дважды** (`artifact_usage`);
- у каждого «плохого» артефакта есть ≥ 1 `hard`-риск и `evidence_anchor`, на который ссылается урок;
- зелёный артефакт (`benign: true`) не имеет `hard`-рисков, а `report` по нему — `soft` (ложное срабатывание);
- до появления корпуса (M2) используется fixture-реестр того же формата (~30 артефактов), чтобы генератор и валидатор не ждали M3;
- смена `corpus_build_id` не ломает старые сценарии: они пиннят свою версию.

## 4. Вехи

### M0. Решения и каркас (итерация 1)

**Задачи:** ADR-0001…0007 (`docs/adr/`); CI на GitHub Actions (5 job'ов) + `docs/ci.md` + `ruff.toml`; threat model v0 (`docs/threat-model.md`); фиксация `ALLOWED_TOPICS`; правило статусов ADR.

**Зачем сейчас:** решения (схема сценария-комнаты, песочница, UI, auth, корпус, CI) определяют БД и API. Переделать их позже — это миграции и переписывание движка. Дешевле зафиксировать на бумаге.

**Риски:** «ещё подумаем» → M1–M3 начнут расходиться; ADR без владельца не соблюдается; CI с слишком строгими правилами станет красным и его начнут игнорировать.

**На что смотреть:** решения должны быть проверяемыми на минимальном примере (10 строк JSON комнаты, 3 страницы корпуса); ADR — не длиннее страницы; линтер стартует с узкого набора правил.

**DoD:** 7 ADR приняты, threat model v0, CI зелёный, `alembic` — одна head.

---

### M1. Ядро правил (итерация 2)

**Задачи:** `rule_snapshot` и версия правила в сценарии; дедуп правил (`(нормализованный текст, topic)`); мягкое удаление документов/правил; API правил с фильтрами; миграции.

**Зачем сейчас:** генератор не может быть надёжнее правил. Пока правило удаляется каскадом, история обучения и аналитика теряются — это дешевле починить сейчас, чем после пилота.

**Риски:** повторная экстракция даст дубли и «размножит» сценарии.

**На что смотреть:** не смешивать `source="baseline"` и `source="document"` в выдаче без приоритета; проверять, что после редактирования документа старые сценарии остаются валидными по `rule_snapshot`.

**DoD:** удаление документа не ломает историю; дубли правил не создаются; тенант без документов видит empty state; генерация не запускается; после загрузки первого документа — запускается.

---

### M2. Генератор сценариев v4 — «комнаты» (итерации 3–5)

**Задачи:** пакет `scenario_generation/` (planner, prompts, pipeline, validators, dedup, scoring); контракт комнаты по ADR-0007 (`objs`, `goal`, `extra`, `ttl`); событийный движок: лента `(действие, объект)` → исход `safe | recovered | compromised | timeout`; метаданные `risk[]`/`benign` в fixture-реестре артефактов; L0–L3 (refs, глаголы по типам, достижимость цели, benign без `hard`); `public`/`private` DTO; `attempts` API с лентой событий; скоринг `max − Σpen − blind`; fallback-пул; лог генерации.

**Зачем сейчас:** это ядро продукта и главный источник брака. Пока комната не проверена на 30 fixture-артефактах, строить UI и корпус рано: они зафиксируют неверные предположения.

**Риски:** цель недостижима (нужный affordance спрятан или за `hard`); LLM ставит `hard` на действие, без которого цель не выполнить; «случайный успех» (report наугад) без benign-кейсов; слишком мало объектов — скучно, слишком много — нечитаемо; `pen`/`lesson` расходятся с текстом урока.

**На что смотреть:** доля комнат, прошедших L3 с первой попытки; распределение исходов (не 90% `safe`); «report-all» даёт низкий балл на benign; длина ленты событий (2–6 действий, а не одно); нет `risk`/`goal` в публичном ответе; `duplicate_rate` на 200 комнатах.

**DoD:** 100 комнат проходят L0–L3; цель достижима во всех; benign-комнаты наказывают ложный report; дубли ≤ 2%; 3 попытки максимум, дальше fallback; клиент не получает ключ ответов.

---

### M3. Веб-корпус 1000 брендов и браузер (итерации 10–11)

**Задачи:** `brands.yaml` сразу на 1000 брендов; генератор на Jinja2 + CSS-токены (4 layout × 8 палитр); мутации 9 типов; пул артефактов ≥ 25 на тему (≥ 450, цель 600) по каналам `site_page/email/pdf/usb_tree/call_script`; `site-service` с allowlist, `/go`, `/sim/forms`, `/trust`; панели доверия; внутренний поиск; iframe-песочница; `corpus_build_id`; тесты консистентности в CI.

**Зачем сейчас:** корпус идёт после ЛК, а не параллельно, потому что до M2 неизвестно, какие поля артефакта реально нужны генератору. Зато к M3 формат уже проверен на fixture-реестре, и 1000 брендов собираются без переделки схемы.

**Риски:** 600 артефактов окажутся однотипными (одно письмо в 600 вариантах); сайты «пластиковые», и сотрудник угадывает по вёрстке; случайный сигнал на легитимной странице учит ложному признаку; новый `build_id` ломает старые сценарии; домены пересекаются с реальными.

**На что смотреть:** тест «ровно N мутаций»; визуальные скриншоты 4×8; сколько уникальных артефактов видит сотрудник за 14 дней; не протекает ли `is_phishing` в HTML/JS/имена файлов; NXDOMAIN-проверка доменов.

**DoD:** 1000 брендов и ≥ 450 артефактов собраны; сборка падает на любом случайном сигнале; браузер работает в песочнице без egress; старые сценарии валидны по своему `build_id`.

---

### M4. Стенд: песочница, ЛК, движок (итерации 7–9 и 12)

**M4a. Песочница сотрудника (итерация 7).** Таблицы состояния на сотрудника: ящик, сообщения, файлы, история браузера, назначения; фильтрация по `employee_id` из сессии; квоты и retention. *Зачем:* без персонального состояния «своя песочница» — это только надпись в UI. *Риски:* чужой ящик через параметр запроса; БД растёт от копий писем. *DoD:* IDOR-тесты, лимиты, сценарий выдаётся конкретному сотруднику.

**M4b. ЛК сотрудника и администратора (итерации 8–9).** SPA (ADR-0003), экран входа; кабинет сотрудника — прогресс, история, разбор своего пути; кабинет админа — отделы, сотрудники, документы, правила, сценарии, предпросмотр. *Зачем:* админ должен увидеть, что генерируется, ещё до движка — иначе брак всплывёт на пилоте. *Риски:* UI начнёт подсказывать вердикт цветом или порядком кнопок; предпросмотр покажет ключ ответов не тому. *DoD:* e2e «логин → кабинет»; RBAC на каждом экране; предпросмотр без `is_correct`.

**M4c. Движок сценариев (итерация 12).** Рендер шага по `kind`; компоненты Mail/Browser/Phone/PDF/USB; панель обратной связи и микро-урок; телеметрия проверок; виртуальный день, слоты, 80/20; e2e. *Зачем:* после корпуса, потому что компоненты должны работать с настоящими артефактами, а не с fixture. *Риски:* 80/20 становится предсказуемым; песочница ломает формы и ввод; сценарий не помещается на экран; сотрудник прокликивает день за 2 минуты. *DoD:* 50 сотрудников проходят 5 дней подряд без блокеров; e2e «правило → сценарий → шаг → ответ → балл».

---

### M5. Рейтинг и аналитика (итерация 13)

**Задачи:** сервис оценки (формула, штрафы, `verified`), уровни, агрегаты отдела, админ-дашборды, детекторы накрутки (report-all, слишком быстро, слив ответов), отчёт по покрытию тем.

**Зачем сейчас:** после M4 есть данные; до пилота нужны метрики, иначе не понять, работает ли обучение.

**Риски:** геймификация демотивирует; «report-all» обходит штраф; руководитель воспринимает баллы как KPI и давит на сотрудников.

**На что смотреть:** `fp_rate` по benign; распределение уровней (не должно быть 90% «экспертов»); жалобы на несправедливость — повод пересмотреть калибровку, а не «усилить дисциплину».

**DoD:** баллы считаются только на сервере; есть отчёт «риск отдела» и тренд; три детектора накрутки дают ложные срабатывания < 5%.

---

### M6. Роли, отделы, multi-tenant (итерация 6)

**Задачи:** сотрудники и отделы, RBAC, `current_principal()`, `tenant_id` из токена (убрать из query/form), профиль отдела (каналы, инструменты, словарь), онбординг тенанта, MFA администратора, тесты IDOR.

**Зачем сейчас:** это дешевле сделать до пилота, чем мигрировать данные после. И это единственный способ закрыть дыру «арендатор приходит от клиента».

**Риски:** смена контракта API ломает `upload.html` и ручные проверки; профиль отдела окажется слишком грубым для «универсальности».

**На что смотреть:** ни один публичный эндпоинт не принимает `tenant_id`; тесты «чужой арендатор → 403/404»; профиль отдела расширяется без миграции (JSON).

**DoD:** IDOR-тесты зелёные; админ без MFA не входит; отдел настраивается без правок кода.

---

### M7. Качество и калибровка (итерация 14)

**Задачи:** эмбеддинг-сервис для near-dup, LLM-judge по рубрике, калибровка `p_correct` и дискриминации, регресс-корпус из 100 сценариев, очередь ручного ревью, A/B-каркас.

**Зачем сейчас:** без калибровки генератор «в среднем нормальный», но отдельные сценарии нерешаемы или тривиальны; на пилоте это выглядит как случайные провалы.

**Риски:** judge смещён (любит длинные тексты, свой же стиль); нет размеченных данных; эмбеддинги стоят GPU.

**На что смотреть:** согласие judge с человеком на 100 парах (цель ≥ 0,7); сценарии с `p_correct > 0,95` и `< 0,15`; дрейф после смены модели.

**DoD:** регресс-корпус в CI; judge-порог откалиброван; есть отчёт по «мёртвым» сценариям.

---

### M8. Безопасность и приватность (непрерывно, закрытие — итерация 15)

**Задачи:** закрыть пп. 1–14 `backlog_security.md`; sandbox-тесты iframe; пентест (внешний или внутренний); DPIA и retention-джоб; шифрованные бэкапы + restore drill; нагрузочный тест; runbook инцидента.

**Зачем сейчас:** безопасность нельзя «добавить в конце» — часть решений (auth, песочница, ground truth) уже в M0/M2/M3, здесь они проверяются и закрываются.

**Риски:** находки пентеста потребуют переделки схемы; бэкапы окажутся невосстановимыми; egress откроется «на время отладки» и останется.

**На что смотреть:** таблица «пункт бэклога → тест/доказательство»; пентест именно стенда (iframe, формы, резолвер) — там самые вероятные дыры.

**DoD:** нет открытых High/Critical; restore drill пройден; DPIA подписан; нагрузка 200 одновременных сессий.

---

### M9. Open-source релиз (итерация 16)

**Задачи:** README и quickstart, compose-профили (`gpu`/`low-vram`/`cpu`), плагин канала (SDK + пример), лицензия, `SECURITY.md`, `CONTRIBUTING.md`, шаблоны ISSUE/PR, release checklist, миграции «с нуля».

**Зачем сейчас:** без упаковки проект остаётся внутренним; open-source — заявленная цель.

**Риски:** релиз с секретами в истории git; неподъёмный quickstart (нужен GPU); нет политики безопасности — уязвимости приходят в issue.

**На что смотреть:** `git log` на секреты (gitleaks по всей истории); запуск с нуля на чистой машине по README; `.env.example` полный.

**DoD:** новый пользователь поднимает стенд за ≤ 30 минут по README; CI публикует образы; security policy опубликована.

## 7. Правила урезания объёма

При отставании режем в этом порядке (сверху — первым):

1. лидерборды и достижения → оставить уровни;
2. 1000 брендов → 300, пул артефактов 600 → 300 (квоты уловок сохраняются);
3. каналы: `search_result` → `web_page` → `phone_call` (email и USB остаются);
4. объектов в комнате 5 → 3, ловушек 6 → 3 (свобода действий не режется — она ядро продукта);
5. админ-дашборды → CSV-выгрузки.

**Не режем:** пункты 8–14 бэклога безопасности, `public`-DTO и серверную оценку, auth/tenancy, `rule_snapshot`, тесты консистентности корпуса.

## 8. Общий Definition of Done

- фича покрыта тестами (unit + один e2e на сценарий использования);
- миграция обратима или описана в `docs/migrations.md`;
- нет новых `tenant_id` из клиента;
- в публичных ответах нет ключа ответов;
- комната проходит L3: цель достижима, `ref` существуют, benign без `hard`, ловушки не блокируют цель;
- документация обновлена (`docs/architecture.md`, ADR при изменении решения);
- метрика фичи видна в дашборде или логе;
- security-чеклист вехи пройден.

**Метрики готовности продукта:** 14-дневное завершение ≥ 80%, `unsafe_rate` падает на второй неделе ≥ 30%, `fp_rate` ≤ 15%, дубли сценариев ≤ 2%, p95 генерации ≤ 20 с, сборка корпуса ≤ 5 мин.
